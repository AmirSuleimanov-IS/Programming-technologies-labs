## Раунд 2 — стек и репозиторий

- **Q6 Бэкенд.** Go 1.26: стандартный `net/http` (маршруты Go 1.22+ с методами и `{id}`), PostgreSQL через `pgx` и обычный SQL, миграции — встроенные `.sql` файлы. Студент уже писал бэкенд на Go, а стандартная библиотека проще Gin и GORM. Форматтер — `gofmt` (в лекции: «Go: вшитый»), линтер — `golangci-lint` v2.
- **Q7 Фронтенд.** React + TypeScript + Vite (минимальный стек из задания), `react-router`, собственный CSS без UI-библиотеки. Линтер — ESLint 10 (flat config), форматтер — Prettier, мёртвый код ищет `knip`.
- **Q8 Монорепозиторий.** Один репозиторий: `backend/` и `frontend/` полностью раздельны (у каждой части свой README, `.gitignore`, `Dockerfile`, конфиги линтера и переменных окружения), в корне — `docker-compose.yml`, `.pre-commit-config.yaml`, общий README. Лекция требует «API и клиент раздельно». Это выполнено разделением папок, а `docker-compose` и pre-commit нужны общими. Обоснование — `docs/adr/0001-monorepo.md`.
- **Q9 Pre-commit.** Фреймворк [pre-commit](https://pre-commit.com) (Python). Встроенные хуки: большие файлы (`check-added-large-files`, 1024 КБ) и маркеры конфликтов (`check-merge-conflict`). Локальные хуки: gofmt, golangci-lint, Prettier, ESLint, `tsc`, knip и проверка имён файлов (`language: fail`). Форматтеры и `eslint --fix` правят файлы сами. Pre-commit останавливает коммит, если файлы изменились, и разработчик проверяет правки и добавляет их заново, как требует задание.
- **Q10 Стандарт имён файлов.** Go — `snake_case.go` (соглашение Go). Фронтенд — `kebab-case` для всех файлов и папок в `src` (`competition-form.tsx`). Компоненты в коде называются в PascalCase, функции и переменные — в camelCase, константы — в UPPER_SNAKE_CASE. Соглашения описаны в README.
- **Q11 Переменные окружения.** Бэкенд читает `.env.<APP_ENV>` (`development` или `production`), переменные процесса важнее файла. В git лежат `.env.development` (без секретов) и `.env.production.example`, сам `.env.production` в `.gitignore`. Фронтенд использует штатные `.env.development` и `.env.production` Vite.
- **Q12 Формат ответов API.** Успех: `{"data": ..., "meta": {...}}`. Ошибка: `{"error": {"code": "VALIDATION_ERROR", "message": "...", "details": [{"field": "...", "message": "..."}]}}`. Коды ответа: 200, 201 (с `Location`), 204 (DELETE), 400 (битый JSON или параметр), 401, 403, 404, 409 (конфликт с состоянием), 422 (ошибки валидации), 500.
- **Q13 Git.** На каждую лабу своя ветка от предыдущей: `lab1-initial-setup`, `lab2-auth-monitoring`, `lab3-caching`, `lab4-testing`. `main` — итоговое состояние. Коммиты атомарные (лекция «Культура коммитов»), формат `тип(где): что сделано` на русском.
- **Q14 GitHub.** Публичный репозиторий `AmirSuleimanov-IS/Programming-technologies-labs` (все репозитории пользователя публичные, преподавателю нужен доступ). Создаётся через API с сохранённым в Git Credential Manager токеном, пушатся все ветки.

## Раунд 3 — предметная модель (см. CONTEXT.md)

- **Q15 Сущности.** Соревнование, Пользователь (роль ADMIN или USER), Заявка (пользователь → соревнование). В лабе 1 есть только Соревнования (CRUD), Пользователи и Заявки добавляются в лабе 2.
- **Q16 Правила заявки.** Подать заявку можно только на соревнование, которое ещё не началось и в котором есть свободные места. Пока предыдущая заявка на рассмотрении или одобрена, вторую подать нельзя. После отмены или отклонения подать снова можно. Администратор одобряет только заявку на рассмотрении и только при наличии свободных мест (проверка в транзакции с блокировкой строки соревнования). Пользователь отменяет свою заявку на рассмотрении или одобренную, пока соревнование не началось. Отклонить можно только заявку на рассмотрении.
- **Q17 Правила соревнования.** Название 3–100 символов, вид спорта 2–50, место 2–100, описание до 1000, лимит мест 1–1000, дата не раньше сегодняшней (проверяется при создании и при изменении даты). Лимит нельзя уменьшить ниже числа одобренных заявок (409). Соревнование нельзя удалить, пока у него есть активные заявки (409).
- **Q18 Пароль и email.** Пароль 8–72 символа (72 байта — предел bcrypt), должен содержать букву и цифру. Email приводится к нижнему регистру и должен быть уникальным (409).

## Раунд 4 — лабы 2–4

- **Q19 Авторизация.** Регистрация (роль всегда USER), вход, bcrypt, JWT (HS256, 12 ч) в заголовке `Authorization: Bearer`. Первый администратор создаётся при старте из `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Токен лежит в `localStorage` — это простое решение с известным риском XSS, он описан в README.
- **Q20 Страницы.** `/login`, `/register`. Страница пользователя `/competitions` (USER и ADMIN): каталог соревнований, подача и отмена заявок, «Мои заявки». Страница администратора `/admin` (только ADMIN): CRUD соревнований, рассмотрение заявок, список пользователей. USER видит только одну защищённую страницу, роль проверяется на бэкенде (middleware) и на фронтенде (защищённый маршрут).
- **Q21 Логи.** `log/slog` в формате JSON в stdout (логи контейнера). Каждый запрос логируется с полями time, level, method, path, status, duration_ms, request_id, user_id. В production уровень не ниже INFO: если `LOG_LEVEL=debug`, он поднимается до INFO с предупреждением. Пароли и токены не логируются.
- **Q22 Метрики.** `prometheus/client_golang`, `/metrics`: `http_requests_total{method,route,status}`, `http_request_duration_seconds`, `http_errors_total{class}`, `auth_attempts_total{result}`. В лабе 3 добавлена `cache_operations_total{cache,result}`. Grafana с provisioning источника и дашборда из файлов.
- **Q23 Кэш бэкенда.** Redis, стратегия cache-aside. Соревнование по id хранится под ключом `competition:{id}` с TTL 5 мин и удаляется при записи (delete on write). Список хранится под ключом `competitions:list:v{N}:{query}` с TTL 60 с, инвалидация — сменой версии (versioned keys). TTL с джиттером ±10% (формула из лекции). В ответе соревнования есть число свободных мест, поэтому кэш сбрасывается и при изменении статуса заявок. Защита от stampede — `singleflight`. Если Redis недоступен, запрос идёт в БД (fail-open), в ответе `X-Cache: BYPASS`, в логах ошибка. Источник данных виден в заголовке `X-Cache` и в поле `meta.cache`. Пользователи и заявки не кэшируются — причины описаны в отчёте 3.
- **Q24 Кэш фронтенда.** Свой модуль кэша в памяти вкладки с TTL 30 с для каталога соревнований. Инвалидация — при любой записи (создание, изменение, удаление, заявки) и при выходе из системы. На странице показан источник: «кэш браузера», «сервер: Redis HIT» или «сервер: БД (MISS)».
- **Q25 Тесты.** Unit-тесты рядом с кодом (`go test ./internal/...`), integration — в `backend/tests/integration` с PostgreSQL и Redis в контейнерах testcontainers (основная БД не используется). Группы запускаются скриптом `backend/scripts/test.sh <группа>` (unit, integration, smoke, regression, auth, competitions, applications, cache). Фронтенд тестируется Vitest (кэш и правила доступа). План покрытия — `docs/test-plan.md`. CI в GitHub Actions: линтеры и unit-тесты на каждый push, integration тоже на каждый push (быстро, ~1 мин).

## Обходные пути и отклонения

- **oxlint → ESLint.** Свежий шаблон `npm create vite` ставит линтер oxlint. Он заменён на ESLint: лекция называет связку «prettier + eslint», а у ESLint есть плагин автоудаления неиспользуемых импортов и правило соглашений об именах.
- **Проверка имён файлов без плагина ESLint.** `eslint-plugin-check-file` тянет пакет `braces` с уязвимостью высокого уровня, для которой нет исправления (`npm audit`). Поэтому имена файлов проверяют два хука pre-commit `language: fail` с регулярными выражениями — одинаково для Go и фронтенда и без зависимостей.
- **Lock-файл фронтенда пересоздан.** С lock-файлом из шаблона `npm ci` в Docker (Linux) падал: не хватало необязательных пакетов `@emnapi/*`. После `rm -rf node_modules package-lock.json && npm install` сборка проходит.
- **Кириллица в curl.** curl.exe в Windows передаёт аргументы в кодировке CP1251, и PostgreSQL отвечал ошибкой на невалидный UTF-8 в параметре `sport` (было 500). Теперь бэкенд сам проверяет параметры и отвечает 400. Демонстрационные запросы для отчётов шлёт `tools/api-demo.mjs` (Node.js, UTF-8), а не curl.
- **Prettier и для документации.** Второй хук `prettier-docs` форматирует Markdown, YAML и JSON вне `frontend/`, чтобы оформление всех файлов проекта было единым (требование лекции).
- **Vite и IPv6.** На этом компьютере сокет [::1] запрещён политикой безопасности, а Vite по умолчанию слушал только ::1. Для скриншотов dev-сервер запускается с `--host 127.0.0.1`.
- **Время ответа на вход.** При проверке оказалось, что вход с неизвестным email отвечает быстрее, чем с неверным паролем (нет bcrypt-сравнения), и по времени можно узнать, зарегистрирован ли адрес. Добавлено сравнение с фиктивным хешем, оба ответа занимают около 70 мс.
- **Шум /metrics в логах.** Prometheus опрашивает /metrics каждые 5 с. Успешные запросы к /metrics и /api/health пишутся на уровне DEBUG, в production их не видно.
- **Действующий уровень логов.** В логе старта сначала печатался запрошенный уровень (DEBUG) даже в production. Теперь печатается действующий (INFO).
- **Пустые страницы в отчётах.** Разрыв страницы перед разделом был отдельным абзацем и давал пустую страницу, если предыдущий раздел заканчивался ровно в конце листа. Теперь это свойство заголовка (page_break_before). Отчёт лабы 1 пересобран в ветке lab2 и дальше.
- **Grafana и Prometheus.** Образы grafana/grafana:12.0.2 и prom/prometheus:v3.5.0. Пароль Grafana admin/admin задаётся в docker-compose только для локального запуска.
- **Данные для дашборда** даёт скрипт tools/traffic.mjs (смесь обычных запросов, ошибок и входов), сброс демо-данных — tools/reset-demo.sh.
- **Падения Docker Desktop (моя ошибка).** Дважды Docker Desktop падал целиком. Причина: служебный скрипт перезапуска локального бэкенда завершал процесс, слушающий порт 8090, а когда бэкенд запущен в контейнере, этот порт слушает прокси Docker Desktop (com.docker.backend). Скрипт `tools/restart-backend.sh` исправлен: он завершает только свой `api.exe` и отказывается работать, если 8090 занят чужим процессом. Восстановление: остановка процессов Docker Desktop, `wsl --shutdown`, запуск заново. Тома с данными сохранились.
- **Долгий BYPASS при отказе Redis.** go-redis по умолчанию делает 5 попыток соединения (DialerRetries) и 3 повтора команды (MaxRetries), и запрос при остановленном Redis ждал 4–8 с. Повторы отключены (MaxRetries=-1, DialerRetries=1), таймауты сокращены, после ошибки кэш 5 с не обращается к Redis (простой circuit breaker). Первый запрос после отказа ждёт около 300 мс, следующие — нет.
- **Двойной запрос на клиенте.** React StrictMode в режиме разработки запускает эффект дважды, и два одинаковых запроса уходили на сервер одновременно. Добавлено объединение одинаковых запросов (inflight) — аналог singleflight на клиенте.
- **Демонстрация TTL.** Чтобы не ждать 5 минут, истечение TTL показано на копии бэкенда на порту 8095 с `CACHE_ITEM_TTL=5s`.
- **Уровень логов кэша.** hit, miss, set, invalidate — INFO, чтобы их было видно в production (требование задания), error — ERROR, пропуск Redis во время паузы — DEBUG (иначе по строке на запрос). При высокой нагрузке hit/miss стоило бы перевести в DEBUG и смотреть на метрику cache_operations_total.
- **Подзаголовки в отчётах** держатся со следующим абзацем (keep_with_next), отчёты 1–3 пересобраны.
- **Lock-файл фронтенда — из Linux-контейнера.** После добавления Vitest CI снова упал на `npm ci` (те же пакеты `@emnapi/*`). Теперь lock-файл обновляется командой `npm install --package-lock-only` в контейнере node:24-alpine. Проверено: `npm ci` проходит и в Linux, и в Windows.
- **Мутационная проверка тестов** выполнялась вручную: ошибка вносилась в код, запускались тесты, файл возвращался через `git checkout`. Результаты — в отчёте 4.
