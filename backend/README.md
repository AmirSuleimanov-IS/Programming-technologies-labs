# SportReg — backend

REST API системы записи на спортивные соревнования. Администратор (роль `ADMIN`) ведёт каталог соревнований и рассматривает заявки. Пользователь (роль `USER`) смотрит каталог, подаёт и отменяет свои заявки. Данные хранятся в PostgreSQL. Бэкенд пишет структурированные логи и отдаёт метрики Prometheus. Термины — в [CONTEXT.md](../CONTEXT.md).

## Структура

Код разбит по модулям предметной области. Внутри модуля — слои «контроллер → сервис → репозиторий» из лекции «Инженерный старт проекта».

```
backend/
├── cmd/api/main.go            # точка входа: конфигурация, БД, маршруты, HTTP-сервер
├── internal/
│   ├── apperr/                # ошибки бизнес-логики (вид ошибки → HTTP-код)
│   ├── application/           # модуль «Заявки»: статусная модель (rules.go), транзакции с блокировкой
│   ├── auth/                  # регистрация, вход, bcrypt, JWT, Guard (проверка роли)
│   ├── cache/                 # cache-aside в Redis: логи, метрики, singleflight, пауза при сбое
│   ├── competition/           # модуль «Соревнования»
│   │   ├── handler.go         #   контроллер: HTTP ↔ сервис
│   │   ├── service.go         #   сервис: бизнес-правила
│   │   ├── repository.go      #   репозиторий: SQL-запросы к PostgreSQL
│   │   ├── model.go           #   модель и DTO запроса
│   │   └── validation.go      #   проверка полей
│   ├── config/                # чтение .env.<APP_ENV> и переменных окружения
│   ├── database/              # подключение, миграции (migrations/*.sql), демо-данные
│   ├── httpapi/               # общий формат ответов, разбор JSON, middleware
│   ├── observability/         # логгер slog, request_id, журнал доступа, метрики Prometheus
│   └── user/                  # учётные записи, роли, текущий пользователь запроса
├── .env.development           # настройки разработки (в git)
├── .env.production.example    # образец настроек production
├── .golangci.yml              # правила линтера
└── Dockerfile
```

## Установка и запуск

Нужны Go 1.26+ и PostgreSQL 17 (проще всего — из `docker-compose.yml` в корне репозитория).

```bash
# из корня репозитория: только база данных
docker compose up -d db

# из папки backend
go run ./cmd/api                 # APP_ENV=development → читается .env.development
```

API будет доступен на http://localhost:8090/api. При старте применяются миграции. В режиме разработки пустой каталог заполняется демо-соревнованиями.

Проверки:

```bash
gofmt -l .                       # форматирование (пустой вывод — всё отформатировано)
golangci-lint run ./...          # линтер
go build ./...
```

Запуск в production-режиме: `APP_ENV=production go run ./cmd/api` (нужен `.env.production` или переменные окружения).

## API

Все ответы — JSON в едином формате.

```jsonc
// успех
{ "data": { ... }, "meta": { "count": 5 } }      // meta — только у списков
// ошибка
{ "error": { "code": "VALIDATION_ERROR", "message": "Данные не прошли проверку",
             "details": [ { "field": "capacity", "message": "от 1 до 1000" } ] } }
```

Защищённые маршруты требуют заголовок `Authorization: Bearer <JWT>`. Токен выдаёт `POST /api/auth/login`.

| Метод  | URL                                         | Доступ      | Описание                                                           | Успех            |
| ------ | ------------------------------------------- | ----------- | ------------------------------------------------------------------ | ---------------- |
| GET    | `/api/health`                               | все         | проверка сервера и БД                                              | 200              |
| GET    | `/metrics`                                  | все         | метрики Prometheus                                                 | 200              |
| POST   | `/api/auth/register`                        | все         | регистрация (роль всегда USER)                                     | 201              |
| POST   | `/api/auth/login`                           | все         | вход, ответ — `token`, `expires_at`, `user`                        | 200              |
| GET    | `/api/auth/me`                              | USER, ADMIN | владелец токена                                                    | 200              |
| GET    | `/api/competitions?q=&sport=`               | USER, ADMIN | каталог с `free_places`                                            | 200              |
| GET    | `/api/competitions/{id}`                    | USER, ADMIN | одно соревнование                                                  | 200              |
| POST   | `/api/competitions`                         | ADMIN       | создать                                                            | 201 + `Location` |
| PUT    | `/api/competitions/{id}`                    | ADMIN       | заменить целиком                                                   | 200              |
| PATCH  | `/api/competitions/{id}`                    | ADMIN       | изменить переданные поля                                           | 200              |
| DELETE | `/api/competitions/{id}`                    | ADMIN       | удалить (если нет активных заявок)                                 | 204              |
| GET    | `/api/applications/my`                      | USER, ADMIN | мои заявки                                                         | 200              |
| POST   | `/api/applications`                         | USER, ADMIN | подать заявку `{"competition_id": 1}`                              | 201              |
| PATCH  | `/api/applications/{id}`                    | USER, ADMIN | `{"status": "cancelled"}` — автор; `approved` / `rejected` — ADMIN | 200              |
| GET    | `/api/applications?status=&competition_id=` | ADMIN       | все заявки                                                         | 200              |
| GET    | `/api/users`                                | ADMIN       | учётные записи                                                     | 200              |

Коды ошибок:

| Код | `error.code`                                                                                                                                                       | Когда                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| 400 | `BAD_REQUEST`                                                                                                                                                      | некорректный JSON, неизвестное поле, нечисловой `id`, параметры не в UTF-8 |
| 401 | `UNAUTHORIZED`                                                                                                                                                     | нет токена, токен недействителен или истёк, неверный email или пароль      |
| 403 | `FORBIDDEN`                                                                                                                                                        | роль не позволяет выполнить действие                                       |
| 404 | `NOT_FOUND`                                                                                                                                                        | нет такого соревнования, заявки или маршрута                               |
| 405 | `METHOD_NOT_ALLOWED`                                                                                                                                               | метод не поддерживается для маршрута                                       |
| 409 | `EMAIL_TAKEN`, `DUPLICATE_APPLICATION`, `NO_FREE_PLACES`, `COMPETITION_STARTED`, `INVALID_STATUS_TRANSITION`, `CAPACITY_BELOW_APPROVED`, `HAS_ACTIVE_APPLICATIONS` | действие противоречит текущему состоянию                                   |
| 422 | `VALIDATION_ERROR`                                                                                                                                                 | поля не прошли проверку (список в `details`)                               |
| 500 | `INTERNAL_ERROR`                                                                                                                                                   | непредвиденная ошибка (подробности только в логе)                          |

Правила заявок: подать можно, пока соревнование не началось и есть свободные места; у пользователя не больше одной активной (на рассмотрении или одобренной) заявки на соревнование; одобрить можно только заявку на рассмотрении и только при свободном месте; отменить — свою заявку на рассмотрении или одобренную. Пароль — от 8 символов, не больше 72 байт, буква и цифра.

Правила полей соревнования: `title` 3–100 символов, `sport` 2–50, `location` 2–100, `description` до 1000, `capacity` 1–1000, `starts_on` — дата `ГГГГ-ММ-ДД` не раньше сегодняшней.

## Кэширование

Стратегия — **cache-aside** (lazy loading): сервис сначала читает Redis, при промахе идёт в PostgreSQL и кладёт результат в Redis с TTL. Код — `internal/cache` (общий механизм) и `internal/competition/cache.go` (ключи, TTL, инвалидация).

| Что                          | Ключ                                 | TTL                           | Инвалидация                                                                                                          |
| ---------------------------- | ------------------------------------ | ----------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| одно соревнование            | `competition:{id}`                   | `CACHE_ITEM_TTL` = 5 мин ±10% | удаление ключа (delete on write) при PUT, PATCH, DELETE соревнования и при одобрении или отмене одобренной заявки    |
| результат поиска по каталогу | `competitions:list:v{N}:q=…:sport=…` | `CACHE_LIST_TTL` = 60 с ±10%  | смена версии `competitions:list:version` (versioned keys): все старые списки сразу недоступны и сами исчезнут по TTL |

Почему кэшируется каталог: его читают все пользователи на каждой загрузке страницы, а меняет редко один администратор (высокое отношение чтений к записям). Данные одинаковы для всех пользователей, поэтому один ключ обслуживает всех. Свободные места меняются чаще, чем сами соревнования, поэтому одобрение заявки тоже сбрасывает кэш.

Почему не кэшируются заявки и пользователи: «мои заявки» у каждого свои (ключ на пользователя — много ключей и мало повторных чтений), а решения об одобрении должны приниматься по актуальным данным. Проверка свободных мест при подаче и одобрении всегда идёт в БД в транзакции, поэтому устаревший кэш не может привести к превышению лимита.

Защитные механизмы:

- **TTL с джиттером ±10%** по формуле из лекции: ключи, записанные одновременно, не истекают одновременно.
- **singleflight**: одновременные промахи по одному ключу дают один запрос к БД (защита от cache stampede).
- **fail-open и пауза**: при ошибке Redis ответ берётся из БД (`X-Cache: BYPASS`), следующие 5 с Redis не опрашивается, чтобы запросы не ждали таймаута. Соединение — с короткими таймаутами, без повторов. Инвалидация пробует удалить ключ даже во время паузы.
- **maxmemory 64 МБ, allkeys-lru** (в `docker-compose.yml`): при нехватке памяти вытесняются давно не использованные ключи. Сохранение на диск выключено: после перезапуска Redis кэш просто пустой.
- **Нормализация ключей списков**: поиск в БД не зависит от регистра, поэтому `?sport=Футбол` и `?sport=футбол` — один ключ.

Источник ответа виден клиенту: заголовок `X-Cache: HIT | MISS | BYPASS` и поле `meta.cache` у `GET /api/competitions` и `GET /api/competitions/{id}`. Каждая операция пишется в лог (`cache hit`, `cache miss`, `cache set`, `cache invalidate` — INFO, `cache error` — ERROR, с полями `cache`, `key`, `result`) и считается в метрике `cache_operations_total{cache,result}`. Ответы API идут с `Cache-Control: no-store`, чтобы браузер и прокси не кэшировали их сами.

Риски, которые остаются: окно устаревания (если ключ был записан параллельно с инвалидацией или Redis был недоступен во время записи, данные устаревают до конца TTL); много ключей у списков (произвольный текст поиска — каждый запрос свой ключ, это ограничивают короткий TTL и LRU); промахи для несуществующих id не кэшируются (cache penetration — при атаке на `/competitions/{случайный id}` запросы идут в БД, решение — короткий отрицательный кэш или rate limit).

## Логирование и метрики

Логи — JSON в stdout (в Docker — логи контейнера). В каждой записи есть время, уровень и сообщение, а в записях внутри HTTP-запроса — ещё `method`, `path`, `request_id` и `user_id`. Строка журнала доступа добавляет `route`, `status` и `duration_ms`. Заголовок `X-Request-ID` возвращается клиенту.

| Уровень | События                                                                                           |
| ------- | ------------------------------------------------------------------------------------------------- |
| DEBUG   | начало запроса, успешная проверка доступа (только в разработке)                                   |
| INFO    | успешный вход, создание пользователя, соревнования, заявки, смена статуса заявки, запросы 2xx/3xx |
| WARN    | неуспешный вход, запрос без токена, недействительный токен, отказ 403, ответы 4xx                 |
| ERROR   | ответы 5xx, паника, непредвиденные ошибки                                                         |

В production уровень не ниже INFO: `LOG_LEVEL=debug` поднимается до `info` с предупреждением. Пароли и токены не логируются, email при неуспешном входе маскируется (`iv***@mail.ru`).

Метрики на `/metrics`: `http_requests_total{method,route,status}`, `http_request_duration_seconds{method,route}` (гистограмма), `http_errors_total{class,route}` (4xx/5xx), `auth_attempts_total{result}` (входы success/failure), `auth_denied_total{reason}` (no_token, invalid_token, forbidden). Метка `route` — шаблон маршрута, а не путь, чтобы не плодить временные ряды на каждый id.

## Соглашения о коде

- Форматирование — только `gofmt`, импорты группируются `goimports` (сначала стандартная библиотека, потом внешние пакеты, потом `sportreg/...`).
- Файлы — `snake_case.go`, пакеты — одно слово в нижнем регистре (`competition`, `httpapi`).
- Переменные и функции — `camelCase`, экспортируемые — `PascalCase`, аббревиатуры целиком (`ID`, `HTTP`, `URL`). Проверяет правило `var-naming` линтера revive.
- Ошибки оборачиваются с контекстом: `fmt.Errorf("list competitions: %w", err)`. Клиенту уходит только `apperr.Error`, остальное — 500 с записью в лог.
- Комментарии и тексты для пользователя — на русском, идентификаторы — на английском.

## Неочевидные решения

- **Стандартный `net/http` вместо фреймворка.** С Go 1.22 маршрутизатор понимает метод и параметры пути (`GET /api/competitions/{id}`), поэтому Gin не нужен. Текстовые ответы 404/405 стандартного маршрутизатора подменяются JSON в middleware `httpapi.JSONErrors`.
- **Обычный SQL вместо ORM.** Запросов мало, SQL виден целиком и легко проверяется. Дата хранится как `DATE`, а в API ходит строкой `ГГГГ-ММ-ДД` (`to_char` в запросе), без часовых поясов.
- **422 для ошибок валидации, 400 для синтаксических.** Клиент отличает «запрос не разобран» от «данные не подходят под правила» и показывает ошибки рядом с полями формы.
- **PUT и PATCH.** PUT заменяет соревнование целиком (непереданное описание становится пустым), PATCH меняет только переданные поля. В DTO поля — указатели, чтобы отличить «не передано» от пустой строки или нуля.
- **Дата в прошлом.** При создании дата должна быть не раньше сегодняшней. При изменении она проверяется, только если её меняют, иначе нельзя было бы поправить описание прошедшего соревнования.
- **Роли проверяются на бэкенде в `auth.Guard`.** Модули получают проверку параметром `user.Guard` и не зависят от пакета `auth`.
- **Гонка за последнее место.** Подача и одобрение заявки идут в транзакции с `SELECT … FOR UPDATE` по строке соревнования, поэтому два одновременных одобрения не займут одно место. Частичный уникальный индекс `applications_one_active_idx` не даёт создать две активные заявки даже при одновременных запросах. Уменьшение лимита и удаление соревнования проверяют условие в том же SQL-запросе.
- **Одинаковые ответ и время для неверного email и неверного пароля.** Для неизвестного email пароль всё равно сравнивается с фиктивным bcrypt-хешем, поэтому по времени ответа нельзя узнать, зарегистрирован ли адрес.
- **Ожидание БД при старте.** В docker-compose PostgreSQL может быть ещё не готов, поэтому `database.Connect` повторяет подключение до 30 секунд.
