# План тестового покрытия SportReg

Цель тестов — не 100% покрытия кода, а уверенность в сценариях, ошибка в которых стоит дороже всего: потеря или порча данных, обход прав доступа, нарушение бизнес-правил (лимит мест, статусы заявок), устаревшие данные из кэша. Приоритет сценария определяется риском: вероятность ошибки × цена ошибки.

Приоритеты: **P1** — тестировать в первую очередь (данные, права, деньги и места, статусы); **P2** — важная функциональность с меньшим риском; **P3** — интерфейс и удобство.

## 2. Что тестировать в первую очередь

1. Права доступа (Guard, матрица маршрутов, правила смены статуса) — ошибка даёт чужим людям чужие данные и решения.
2. Лимит мест и статусная модель заявок, включая гонку одобрений, — главное бизнес-правило системы.
3. Аутентификация: пароль, хеш, JWT.
4. Целостность данных соревнований (PUT/PATCH, запрет удаления и уменьшения лимита).
5. Корректность кэша: инвалидация и отказ Redis.
6. Валидация полей и формат ошибок.

## 3. Виды тестов

| Вид             | Что проверяет                                                                                             | Где                                                                                                                          | Время   |
| --------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------- |
| **unit**        | одну функцию, правило или сервис; БД заменена подделкой в памяти, Redis — miniredis                       | `backend/internal/**/*_test.go`, `frontend/src/**/*.test.ts`                                                                 | секунды |
| **integration** | API + PostgreSQL + Redis вместе: SQL, транзакции, блокировки, уникальные индексы, каскадное удаление, кэш | `backend/tests/integration` (build-тег `integration`), БД и Redis в контейнерах testcontainers — основная БД не используется | ~20 с   |
| **smoke**       | «счастливый путь»: сервер жив, БД доступна, вход и каталог работают                                       | `TestSmoke_*`                                                                                                                | секунды |
| **scenario**    | законченный пользовательский сценарий «успешная заявка»                                                   | `TestScenario_*`                                                                                                             | секунды |
| **regression**  | всё вместе: всё, что работало раньше, работает и сейчас                                                   | все unit + integration                                                                                                       | ~30 с   |

Почему так: правила (валидация, статусы, права) — чистые функции, их дешевле всего проверять unit-тестами с таблицами решений и граничными значениями. То, что обеспечивает БД (уникальный индекс, `FOR UPDATE`, `ON DELETE CASCADE`, условие в `UPDATE`), подделкой не проверить, поэтому для этого нужны integration-тесты на настоящей PostgreSQL. Мутационная проверка (удаление `FOR UPDATE`) показала, что без блокировки одобряются все 6 заявок на 2 места, а unit-тест с подделкой этого не заметил бы.

## 4. Группы, команды и когда запускать

| Группа                                          | Команда                             | Когда                                                                          |
| ----------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------ |
| `unit`                                          | `scripts/test.sh unit` · `npm test` | при каждом изменении кода, локально и в CI                                     |
| `integration`                                   | `scripts/test.sh integration`       | перед слиянием ветки, в CI на каждый push                                      |
| `smoke`                                         | `scripts/test.sh smoke`             | после сборки и развёртывания                                                   |
| `scenario`                                      | `scripts/test.sh scenario`          | перед слиянием, после развёртывания                                            |
| `regression`                                    | `scripts/test.sh regression`        | перед сдачей лабораторной и релизом                                            |
| `validation`                                    | `scripts/test.sh validation`        | при изменении правил полей                                                     |
| `access`                                        | `scripts/test.sh access`            | при изменении ролей, маршрутов и статусной модели                              |
| `auth`, `competitions`, `applications`, `cache` | `scripts/test.sh <сущность>`        | при работе над конкретной сущностью                                            |
| `coverage`                                      | `scripts/test.sh coverage`          | для информации: покрытие не показывает качество тестов (лекция «Тестирование») |

Команды `scripts/test.sh` выполняются из папки `backend`. Unit-тесты быстрые и не требуют Docker, поэтому их запускают часто. Integration-тесты требуют Docker и занимают десятки секунд, поэтому их запускают реже: перед слиянием и в CI. Проверка в GitHub Actions (`.github/workflows/ci.yml`) запускает линтеры, unit- и integration-тесты бэкенда и фронтенда и сборку на каждый push.

## 5. Что пока не покрыто и почему

| Не покрыто                                                              | Почему                                                                                           | Чем закрыть позже                                                    |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| поиск и фильтр каталога (`ILIKE`, регистр вида спорта)                  | низкий риск: ошибка даёт неверную выдачу, но не портит данные                                    | integration-тест репозитория с несколькими соревнованиями            |
| миграции «с нуля» на пустой БД                                          | косвенно проверены: каждый запуск integration-тестов применяет все миграции к новому контейнеру  | отдельный тест повторного применения (идемпотентность)               |
| демо-данные `SeedDemo`                                                  | используются только в разработке                                                                 | —                                                                    |
| метрики Prometheus (имена, метки)                                       | наблюдаемость, а не бизнес-логика; проверено вручную на дашборде                                 | unit-тест с `testutil.CollectAndCompare`                             |
| React-компоненты и страницы (формы, защищённые маршруты, выход при 401) | UI меняется часто, тесты компонентов хрупкие; правила вынесены в чистые функции, которые покрыты | Testing Library для форм; e2e (Playwright) для входа и подачи заявки |
| e2e в браузере через весь стек                                          | дорогие и медленные; сценарий на уровне API уже покрыт integration-тестом                        | Playwright-сценарий «вход → заявка → одобрение» перед релизом        |
| нагрузка, производительность кэша                                       | для учебного проекта достаточно замера `tools/cache-bench.mjs`                                   | k6 или vegeta с порогами по p95                                      |
| сборка и запуск Docker-образов                                          | проверяется вручную `docker compose up`                                                          | smoke-тест против поднятого compose в CI                             |

## 6. Приёмы тест-дизайна из лекции

- **Граничные значения**: пароль 7/8 символов и 72/73 байта, название 2/3 и 100/101 символ, места 0/1 и 1000/1001, свободные места 0/1, дата вчера/сегодня/завтра, TTL за 1 мс до и в момент истечения.
- **Классы эквивалентности**: корректный email, email без домена, email с отображаемым именем; токен корректный, подделанный, просроченный.
- **Таблица решений**: смена статуса заявки (исходный статус × целевой × автор × администратор), матрица «маршрут × роль».
- **Негативные сценарии и ошибки**: каждая integration-группа содержит позитивный и негативный сценарии; после ошибки проверяется, что в БД ничего не изменилось.
