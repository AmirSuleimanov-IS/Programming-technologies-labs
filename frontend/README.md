# SportReg — frontend

Клиент системы записи на спортивные соревнования: SPA на React, работающее с REST API бэкенда.

## Страницы и роли

| Адрес           | Доступ      | Что на странице                                                                       |
| --------------- | ----------- | ------------------------------------------------------------------------------------- |
| `/login`        | все         | вход                                                                                  |
| `/register`     | все         | регистрация (после неё — автоматический вход)                                         |
| `/competitions` | USER, ADMIN | страница пользователя: каталог соревнований, подача заявки, «Мои заявки» с отменой    |
| `/admin`        | ADMIN       | страница администратора: заявки (одобрить/отклонить), CRUD соревнований, пользователи |
| `/forbidden`    | все         | 403 — сюда попадает USER, открывший страницу администратора                           |

Защищённые маршруты обёрнуты в `ProtectedRoute`. Гость попадает на `/login`, а после входа возвращается на страницу, которую открывал. Пользователь без нужной роли попадает на `/forbidden`. Шапка показывает только доступные роли ссылки. Это проверка для удобства интерфейса, а настоящую защиту даёт бэкенд: он сам проверяет JWT и роль на каждом запросе. Матрица доступа — `src/constants/routes.ts`.

Сессия (JWT, срок действия и пользователь) хранится в `localStorage` и переживает перезагрузку страницы. Если сервер отвечает 401 на запрос с токеном (токен истёк), клиент выходит из системы. Риск хранения токена в `localStorage` — его может прочитать скрипт при XSS-уязвимости. Для учебного проекта это принято осознанно, а альтернатива — cookie `HttpOnly` с защитой от CSRF.

## Кэш на клиенте

Каталог соревнований кэшируется в памяти вкладки (`src/utils/query-cache.ts`, стратегия cache-aside с TTL):

- ключ — фильтр каталога (`competitions?q=…&sport=…`), TTL — `VITE_CACHE_TTL_SECONDS` (30 с);
- одинаковые запросы, отправленные одновременно, объединяются в один (`inflight` в `competitions-api.ts`);
- инвалидация: после создания, изменения и удаления соревнования, после подачи, отмены и рассмотрения заявки (меняются свободные места) — удаляются все ключи `competitions*`; при входе и выходе кэш очищается целиком;
- кэш живёт только в памяти: после перезагрузки страницы он пуст, на диск и в `localStorage` данные не попадают.

Над каталогом показывается источник данных: «кэш браузера» (с возрастом записи), «сервер, кэш Redis (HIT)», «сервер, база данных (MISS)» или «… Redis недоступен (BYPASS)» — по полю `meta.cache` ответа. Кнопка «Обновить с сервера» сбрасывает кэш браузера. Каждая операция пишется в консоль браузера с префиксом `[cache]`.

Почему 30 секунд: каталог меняется редко, а свободные места — источник возможного устаревания. Подать заявку на соревнование без мест всё равно нельзя: сервер проверяет места в транзакции и ответит 409, а после любого своего действия клиент сбрасывает кэш.

## Структура

Структура `src` повторяет схему из лекции «Инженерный старт проекта».

```
frontend/
├── src/
│   ├── main.tsx                 # точка входа
│   ├── app.tsx                  # маршруты
│   ├── api/                     # запросы к REST API
│   │   ├── http-client.ts       #   fetch, токен в Authorization, разбор ответов и ошибок
│   │   └── *-api.ts             #   соревнования, вход, заявки, пользователи
│   ├── assets/styles.css        # стили
│   ├── components/
│   │   ├── ui/                  # базовые элементы (поле формы, статус заявки)
│   │   └── elements/            # составные блоки (шапка, AuthProvider, ProtectedRoute, карточки, таблицы, формы)
│   ├── constants/               # маршруты и роли страниц, названия статусов, подсказки видов спорта
│   ├── hooks/                   # useAuth, контекст сессии
│   │   └── requests/            #   хуки загрузки данных (useRequest, useCompetitions)
│   ├── pages/                   # страницы: вход, регистрация, пользователь, администратор, 403, 404
│   ├── types/                   # типы данных API
│   └── utils/                   # даты, проверка доступа, хранение сессии
├── public/                      # статические файлы (иконка)
├── .env.development, .env.production
├── eslint.config.js, .prettierrc.json, .prettierignore, knip.json
├── nginx.conf, Dockerfile       # production-образ
└── vite.config.ts
```

## Установка и запуск

Нужен Node.js 24+.

```bash
npm install
npm run dev          # http://localhost:5173, запросы /api проксируются на http://localhost:8090
```

Бэкенд должен быть запущен (см. `backend/README.md` или `docker compose up` в корне).

| Команда                           | Что делает                                            |
| --------------------------------- | ----------------------------------------------------- |
| `npm run build`                   | проверка типов и production-сборка в `dist/`          |
| `npm run preview`                 | просмотр production-сборки                            |
| `npm run lint` / `lint:fix`       | ESLint (без предупреждений) / с автоисправлением      |
| `npm run format` / `format:check` | Prettier: отформатировать / проверить                 |
| `npm run typecheck`               | TypeScript без сборки                                 |
| `npm run knip`                    | поиск неиспользуемых файлов, экспортов и зависимостей |

## Тесты

`npm test` — unit-тесты Vitest (`src/**/*.test.ts`, рядом с кодом): кэш браузера (TTL, инвалидация, объединение одинаковых запросов), матрица доступа к страницам, отбор изменённых полей для PATCH. `npm run test:watch` — перезапуск при изменениях, `npx vitest run cache` — только тесты с «cache» в имени файла. План покрытия — [docs/test-plan.md](../docs/test-plan.md).

## Переменные окружения

Vite подставляет переменные с префиксом `VITE_` в код при сборке: `npm run dev` берёт их из `.env.development`, `npm run build` — из `.env.production`. Секретов в них нет, оба файла лежат в git. Локальные переопределения — в `.env.*.local` (в `.gitignore`).

| Переменная               | development             | production | Описание                                                                         |
| ------------------------ | ----------------------- | ---------- | -------------------------------------------------------------------------------- |
| `VITE_APP_TITLE`         | `SportReg (dev)`        | `SportReg` | название в шапке                                                                 |
| `VITE_API_URL`           | `/api`                  | `/api`     | префикс запросов к API                                                           |
| `BACKEND_URL`            | `http://localhost:8090` | —          | куда Vite проксирует `/api` (только для `vite.config.ts`, в браузер не попадает) |
| `VITE_CACHE_TTL_SECONDS` | `30`                    | `30`       | время жизни записей кэша каталога в браузере, секунд                             |

## Соглашения о коде

- Файлы и папки в `src` — **kebab-case** (`competition-form.tsx`, `use-competitions.ts`). Проверяет хук pre-commit `file-names-frontend`.
- Компоненты и типы — `PascalCase`, функции, переменные и хуки — `camelCase` (хуки начинаются с `use`), константы модуля — `UPPER_SNAKE_CASE`. Проверяет правило ESLint `@typescript-eslint/naming-convention`.
- Именованные экспорты, без `export default` (кроме конфигов инструментов).
- Форматирование — Prettier: одинарные кавычки, без точек с запятой, ширина 100.
- Поля ответов API остаются как в JSON (`starts_on`), чтобы не переименовывать их при каждом запросе.

## Неочевидные решения

- **Прокси вместо CORS.** В разработке `/api` проксирует Vite, в Docker — nginx. Браузер видит один источник, поэтому бэкенду не нужны CORS-заголовки.
- **PATCH при изменении.** Форма отправляет только изменённые поля (`changedFields` в `competitions-page.tsx`), поэтому правка одного поля не перезаписывает чужие одновременные изменения других полей.
- **Ошибки валидации у полей.** Бэкенд возвращает 422 со списком `details[]`, и форма показывает каждое сообщение под своим полем.
- **Lock-файл создаётся в Linux.** npm в Windows не записывает в `package-lock.json` необязательные пакеты `@emnapi/*`, нужные Linux, и `npm ci` в Docker и CI падает. После изменения зависимостей lock-файл обновляется в контейнере: `docker run --rm -v "$PWD":/app -w /app node:24-alpine npm install --package-lock-only`. Такой lock-файл подходит и для Windows.
